# The size of every binary a release ships, and the budget it is held to.
# tools/size_check.py reads it in a step of every release job, right after the
# binary is final -- after UPX, where UPX applies -- and the lint job checks the
# file itself on every push.
#
#   binary    a target of tools/configure.py, or android/<abi>: one line for
#             each native library the Android bundle carries
#   kind      what the file is, read off its first bytes: elf, pe, macho, wasm,
#             or so for an Android library
#   unpacked  bytes as the linker wrote it: build/release/<name>, the .wasm,
#             the .so as it sits in the .aab
#   packed    bytes of the copy that ships, after UPX, for a target [upx] packs;
#             - where UPX does not apply
#
# THE RULE (Omar, 2026-10-11). Each number is the size measured on the commit
# its comment names. Within 1.5% of it, either way, a binary passes in
# silence. Past that it still passes, with a warning that names the new
# number -- on the run's summary page as well as in its log -- and past 10% it
# fails. Over is a growth nobody wrote down; under is a stale line, which
# hides the next growth. Growing is allowed: it is a decision, and this file
# is where it is written down, in the commit that makes it.
#
# Every check prints the measured line in this file's own format, ending in
# "# measured at <commit>", pass or fail, so one CI run's log is one commit:
#     gh run view <run> --log | python3 tools/size_check.py --update -
#
# ? is a size nobody has measured yet: the job that builds it fails and prints
# the line to paste. macOS and the BSDs build only in CI, and only on a full
# run. A comment that says "estimate" is a size worked out from an older
# measurement, not read off this build; it is held to the same rule until a
# run's log replaces it.
#
